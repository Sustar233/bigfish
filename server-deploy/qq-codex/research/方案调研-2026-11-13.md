# 普通 QQ 小号接入 Codex：方案调研

调研日期：2026-11-13。目标小号 1000000002，只允许 1000000001 的好友私聊。此次只做公开资料核查和本地静态检查，未修改服务器、登录 QQ 或发送 QQ 消息。

## 建议

优先验证 **NapCat v4.18.42 社区归档 + 已准备的私人聊天桥 + 服务器现有 Codex CLI**。这是候选方案，尚未通过真实登录验证。QQ 登录组件是当前主要不确定项；不能把“源码接口相符”当作“已经能收发消息”。

链路：大号 QQ → 小号 QQ → NapCat OneBot HTTP/SSE → 私人聊天桥 → Codex CLI → 固定大号 QQ。

继续使用现有 ChatGPT 登录方式，不配置 DeepSeek 或其他付费 API。Codex 调用仍受账号额度、登录状态和网络情况限制。官方说明：[认证](https://learn.chatgpt.com/docs/auth?surface=cli)、[非交互调用](https://learn.chatgpt.com/docs/non-interactive-mode)。

## NapCat 接口检查结果

本地保存了 v4.18.42 的三个源码文件，仅作为阅读副本，没有执行：

- `http-server-sse.ts`：`/_events` 返回 SSE，事件格式为 `data: <JSON>\n\n`；其他路径交由 HTTP action API 处理。
- `http-server.ts`：请求先经过 Token 校验，支持 `Authorization: Bearer ...`；监听地址和端口可配置。
- `onebot-config.ts`：有 `network.httpSseServers`，消息格式默认 `array`。

这些与现有 `../bridge.py` 的事件输入和鉴权方式相符，因此传输层有望复用。真实好友私聊事件、账号身份检查和发送接口仍需登录后验证。

源码基址：`https://raw.githubusercontent.com/XingYunStar/NapCatQQ/v4.18.42/packages/napcat-onebot/`，三个文件分别位于 `network/http-server-sse.ts`、`network/http-server.ts`、`config/config.ts`。另保存的 `qqnt.json` 是仓库的加载模板，里面的旧版本号不能当作完整兼容版本清单。

## 下一阶段验证顺序

1. 完整取得固定版本资产，校验发布摘要，并尽可能用独立保存的摘要或来源交叉核对。先检查镜像配置、启动脚本、二进制、QQ 版本和默认网络暴露情况。
2. 将 QQ 网关放在独立目录或容器中运行。不要把 Codex 登录文件、知乎凭据、邮箱配置挂入 QQ 容器。OneBot 仅监听本机，使用随机 Token；管理页通过 SSH 转发访问。
3. 用用户手机扫描 QQ 登录二维码。确认实际登录账号是 1000000002；此时先不启用自动回复。
4. 核对 `get_login_info`、好友私聊事件、文本数组格式及发送返回值，再启用仅响应 1000000001 的文本聊天桥。
5. 验证正常回复、重复事件、上下文重置、其他账号/群消息被忽略、重启后的登录恢复。通过后再配置长期运行和故障告警。

普通号接入属于第三方实现，可能遇到重新验证、掉线或账号限制。单次登录成功不能证明长期稳定。

## 桥接项目选择

现有私人聊天桥适合当前“仅大号与小号文本聊天”的范围，包含固定发件对象、白名单、事件去重和独立短期上下文。它的 QQ 对接尚未实测。

[QQ-Agent-Bridge](https://github.com/wkj2333666/QQ-Agent-Bridge) 可作为后续文件、图片、任务执行的参考：支持 `custom-cli` 接 Codex，但自身不实现 QQ 登录，还引入 uv、micromamba 和 Bubblewrap 等运行约束。对当前目标，先复用现有小桥更容易定位问题。
